## 6. Failující E2E testy na Horizonu — analýza

### Test 3 „caps excessive values at the app maximum" — příčina: TEST ❌ (appka je OK)

Trace (`test-results/...app-maximum-desktop-retry1/error-context.md`) ukazuje, že
embed odvedl svou práci: input má hodnotu **6**, notice zobrazuje
„Minimum: 2 · Sold in multiples of 2 · Maximum: 6" — a tlačítko
**„Increase quantity" je `[disabled]`**. Horizon (na rozdíl od Dawn) nativně
deaktivuje plus tlačítko, jakmile hodnota == `max`. Test na řádku
`storefront.quantity.spec.ts:101` volá `plus.click()`, Playwright čeká na
enabled a po ~46 s timeoutuje.

**Doporučený fix (v testu):**
```ts
const plus = form.locator("button[name='plus']");
if (await plus.isEnabled()) await plus.click();   // Dawn klikne, Horizon má disabled
await expect(input).toHaveValue("6");
```
případně navíc `await expect(plus).toBeDisabled()` větvení podle témata není
třeba — obě větve dokazují, že cap drží.

### Testy 4–6 „reapplies the variant override after native theme morphing" — příčina: APPKA (embed) ⚠️

Trace ukazuje: varianta **Large je zaškrtnutá**, ale spinbutton má hodnotu **2**
a platí pravidlo min2/step2 první varianty — očekávané override min3/step3/max9
se po morphu nikdy neaplikovalo. Mechanika selhání v
`extensions/won-quantity-storefront/assets/won-quantity.js`:

1. `change` na radiu varianty naplánuje scan za **40 ms** (`l(40)`).
2. Scan přečte variant id z `input[name='id']` — jenže Horizon v té chvíli ještě
   běží asynchronní section re-render (fetch + DOM morph, řádově stovky ms);
   id je stále staré → nafetchuje se config staré varianty a request-key guard
   pak legitimně aplikuje staré pravidlo.
3. Po dokončení morphu už **žádný re-scan nenastane**: MutationObserver sleduje
   jen `childList` (přidané uzly `form`/`input`/`[data-product-id]`), ale Horizon
   morphuje atributy/hodnoty **in-place** — žádné addedNodes, žádný trigger.
   `shopify:section:load` se při variant morphu nevystřelí.

Na Dawn to prochází, protože Dawn přepíše `input[name='id']` synchronně (příp.
přerenderuje formulář = childList mutace).

**Doporučený fix (v embedu, theme-agnostic, neměnit sdílené selektory):**
- V `V()` po `await` config-fetch znovu spočítat `P(t,e)` a pokud se resolved
  `variantId` mezitím změnil, naplánovat další scan místo aplikace (dnes se jen
  porovnává requestKey pořízený PŘED fetch).
- Po `change` eventu plánovat krátkou retry sérii scanů (např. 40 ms → 300 ms →
  800 ms), dokud se variant id nestabilizuje, nebo navíc pověsit `change`
  listener přímo na `input[name='id']`/`variant-picker` a MutationObserver
  rozšířit o `attributes: true, attributeFilter: ["value", "data-product-id"]`
  na formulářích. Retry série je nejmenší bezpečný zásah.

Test samotný je napsaný korektně (čeká na ready marker); po fixu embedu by měl
projít beze změny.
