Hranice portfolia — jedna appka, jeden primitiv

Appky si nesmí splývat. Když se ptáš „kterou appkou to vyřeším?“, nikdy neptej podle marketingové škatulky (spousta appek „zvedá AOV“). Ptej se „čí je to primitiv?“ — každá Won appka vlastní právě jeden a na cizí nesahá. Tím se ti nikdy nepřekryjí.

Won Discounts cenu a odměny (primitiv = sleva): slevy a kódy, množstevní slevy, dárky a doprava zdarma za práh, výprodej, ochrana marže. Test proti splývání: Stepper vlastní ovladač, Won Discounts vlastní cenu a odměny, Companion vlastní doporučení, Toasts vlastní notifikaci, Badges vlastní štítek. Když appka potřebuje cizí primitiv, odkáže ho, nevlastní: Toasts slevu jen oznámí z hotové alokace, Companion doporučuje produkty a existující větší balení; ceny a slevy ponechává merchantovi bez povinné integrace.

Množství = Stepper rozhodnuto 2026-08-07

„Quantity rules“ (MOQ / násobky / max) nejsou samostatná appka — samostatná „Won Quantity“ se ruší. Merchant to vnímá jako jednu věc: jak zákazník volí kolik kusů.

Stepper Free = widget + živý count. Stepper Pro = + pravidla množství (MOQ / násobky / max) přes won.quantity_rules. Stepper stále nesahá na cenu — jen na povolené počty.

Companion ≠ Won Discounts rozhodnuto 2026-08-07

Companion a množstevní slevy vypadají podobně (oba „upsell“), ale je to šířka vs hloubka. Neslévat. Množstevní slevy drží cenu Functionou a od 2026-09-28 jsou modulem Won Discounts (dříve samostatná Won Tiers) — vnořit je do Companionu = zašpinit jeho duši „žádná cenová magie“.

Upřesnění 2026-10-01: Companion je samostatný, bez závislosti na Won Discounts. Nabízí existující produkty a větší varianty; cenu, případné slevy i označení zvýhodnění nastavuje merchant. Automatické navádění na slevové prahy není povinná součást integrace.

Slevy = Won Discounts rozhodnuto 2026-09-28

Tiers, Rewards (GiftLadder + ShipGoal), Outlet a MarginGuard nejsou samostatné appky, ale moduly jedné: Won Discounts. Všechny slevy obchodu jdou přes ni, jen tak engine ví, co se v košíku a v pokladně uplatní.

Discount funkce o sobě nevědí a store jich smí mít max. 25 aktivních, proto slevový hub je tady záměr, ne anti-pattern. Detail: won-discounts/rozhodnuti.md.

0 · Nápad (E+T → produkt): optimistické +/− steppery u každého výskytu produktu — PDP, cart page, drawer, collection karta, search — kde klik na plus/minus přepne UI okamžitě a server se dorovnává na pozadí. Origin je custom klientské řešení Enervit assets/tb-cart-qty.js: steppery .tb-qty-ctrl[data-variant-id], mapa cílových množství desiredQtyMap, agregovaný sync přes /cart/update.js, po chybě re-sync z /cart.js, zámek proti dvojkliku na prvním 0→1 a ignorování dárkových řádků (_gift_progress). Cíl = nejčistší ztělesnění „příjemné na používání": jediné zápisy do košíku jsou user-initiated, žádná Function, žádná manipulace cen — pure-surface widget.

Rozhodnutí / pozicování: ceník flat & levný ($2/mo, žádné usage metry) a úmyslně modulární — jen stepper, ne celá cart-drawer suite. Warm-start recenze sbíráme z reálných eshopů, kde stepper už běží (Enervit + Therabeast). Wedge z auditu: celá cart-UX kategorie je usage-metered — Buy Me měří add-to-carts, sticky-ATC appky měří kliky, takže náklady rostou s trakcí; iCart je navíc delistovaný. Won hraje opačně: flat levná cena (predikovatelná, ne penalizace za úspěch) + genuinely modular (koupíš jen stepper) + rychlý a spolehlivý optimistic (okamžité UI, agregovaný sync, rollback na server-pravdu) + jednodušší UX. Neveme na šířku funkcí, ale „stejná funkčnost, jednodušší používání". Badge: Spec · Scaffold · Alpha · Beta · Shipped.

Sdílený cart-core (@won/core/cart), změna pořadí 2026-10-01: Páteř nejprve postaví Won Companion, po dokončení Won Discounts. Stepper ji následně převezme a zpevní pro vlastní ovládání množství. Plánované rozhraní: cartState, cartAdapter, deriveEvents, optimistic.mutate(op) a won:cart:update. Autorita = skutečný snapshot /cart.js, včetně obnovy po chybách a nejasném timeoutu. Serializace, deduplikace, multi-tab a Dawn/Horizon adaptéry jsou požadavky, nikoli hotové sdílené jádro. Existující zkušenosti a cart diff z Toasts využít bez předstírání, že celá transportní vrstva již existuje.

Brainstorm & rozhodnutí (vyladěno 2026-08): Reach = osa MVP žebříku — „kdekoli je buy CTA nebo manipulace množství → Won Stepper": PDP → cart/drawer → search → collection karty → zbytek. Qty 0: default odebrat z košíku, ale jako toggle (odebrat / disable na 1 / potvrzení); undo deleguj na Toasts, když běží. Quantity rules (MOQ / násobky / max): Stepper zůstává Function-free, pure-surface — Free = inventory cap; Pro čte pravidla z metafieldu won.quantity_rules (snap na násobky, disable na maxu, hint „min N"). Tvrdé vynucení u checkoutu (volitelná Cart Validation Function nad tímtéž won.quantity_rules metafieldem) = Stepper Pro, pozdější hardening-modul — ne samostatná appka (viz „Hranice portfolia": množství vlastní Stepper). Storefront surface zůstává Function-free a rychlý. Free/Pro: Free = steppery všude + živý count + inventory cap + a11y/klávesnice; Pro = quantity rules + segment/collection cílení + appearance tuning + custom CSS. Vzhled z 90 % dědí téma, jen lehký Pro tuning. Dodatečné featury: síťová odolnost (queue/retry/reconcile na flaky mobilu), adopce existujícího theme qty controlu (převzít, ne zdvojit), lazy-mount na gridech (IntersectionObserver), varianta-na-kartě (default / mini-picker), micro-feedback na min/max, přímé zadání čísla na cart page, a toggle „neotvírat boční košík při quick add/remove" (default neotvírat — feedback dá živý count badge / Toasts, ne otevřený drawer).

Požadavek — cross-app awareness v adminu: Stepper funguje nejpříjemněji s Won Toasts (bez otevřeného drawru dá „přidáno" feedback živý count badge / toast). Admin to musí čitelně ukázat: karta/banner „Nejlépe funguje s Won Toasts" s install statusem + odkazem, a když je drawer-auto-open vypnutý a Toasts není nainstalovaný, varovat, že zákazník nedostane feedback o přidání. Obecná zásada (kandidát do ADMIN-UX-PRINCIPLES.md): každá Won appka, co se cross-referencuje na jinou, to vkusně zmíní v adminu (benefit + install status + odkaz) — cross-app awareness, ne adware cross-promo à la konkurence.

Širší úhly (vyladěno 2026-08): Stale totals — stepper změní košík, ale součet na stránce chvíli lže; po reconcile proto vždy emit won:cart:update (téma / ostatní Won appky si repaint řeší samy) a Pro opt-in aktivní refresh přes Section Rendering API (stepper si vyžádá nový HTML cart/totals sekcí a vymění ho) pro témata, co event neposlouchají. Robustnost na ~99 % témat = štěpení rizika: logika je 100% přenositelná (Ajax Cart API je univerzální kontrakt, láme se jen DOM attachment), na to vrstvíme (1) OS2.0 konvence (form[action*="/cart/add"], [name="id"], input[name="quantity"]/updates[], <quantity-input>, řádky s data-key), (2) theme-adapter registry — projet HTML strukturu top N témat (Dawn, Horizon + nejprodávanější) a nakódit přesné selektory; známé téma → precizní adapter, neznámé → heuristika z (1), (3) app block na PDP (merchant položí stepper ručně → obchází auto-detekci), (4) admin selector-override + živý indikátor „detekováno / nedetekováno" na každé ploše, a pojistku safe no-op (když si není jistý, radši nekreslí, než aby rozbil téma). Reconcile = autorita: při server-reject (inventory / Function / cart-limit řádek upraví) vyhrává /cart.js, rollback nenápadný (ne blikání); flush před odchodem (pagehide/visibilitychange), ať se agregovaný sync neztratí při navigaci, a nenápadný „pending" mikro-stav během round-tripu. B2B / wholesale pozice: rychlá manipulace velkých množství, case-packs, přímé zadání čísla a MOQ/násobky = přesně bolest B2B → Stepper je „B2B-friendly qty widget" a most k Won Discounts (množstevní slevy); direct-entry velkých množství = Pro (spolu s quantity rules). Analytika vede k závěrům, ne vanity metrikám: kde se mění množství (PDP/cart/karta = kam dát pozornost), up/down/qty→0 na ploše (removal v draweru = cenový/shipping šok = friction diagnóza), produkty často bumpnuté na 2–3+ = kandidáti na multipack/bundle → krmí Companion bigger-pack a prahy odměn ve Won Discounts, B2B účty s velkými množstvími → insight pro množstevní slevy (Won Discounts). Dva akční závěry: merchandising (co zabalit) + friction (kde ztrácíš košík) — obojí předá dál jiné Won appce. Zralost: spec na úrovni Toasts, ~70 % substrátu zděděno z pilota; nové jen dva rizikové kusy (optimistic.mutate + theme-attachment) → před plným buildem krátký spike: theme-adapter detekce napříč top tématy + optimistic.mutate red-first unit testy.

Ověřeno sweepem 8 Theme Store témat (2026-08): headless Playwright probe (Impact, Concept, Pebble, Purevea, Stack, Fit-Check, Local, Shapes). Nálezy zamykají architekturu: (a) logická vrstva 100% přenositelná — [name="id"] + /cart/add.js+/cart.js fungují 8/8; (b) cart qty = input[name="updates[]"] u 7/8 (jediný outlier Impact = custom <quantity-input> přes /cart/change.js → adapter) → generická heuristika pokryje ~85 %, zbytek ~3 adaptery; (c) PDP qty stepper chybí u 7/8 témat → na PDP jít přes merchant app block, ne auto-detekci (a Stepper tam přidává schopnost, kterou většina témat nemá), drawer/cart = univerzální auto-attach plocha (drawer 6/8, cart-page fallback pro Local/Shapes); (d) line-identity se liší (data-key / data-line / positional) → resolvovat přes nejbližší cart-item předka nebo pořadí z /cart.js, nikdy přes jediný atribut. Reusable theme-sweep.mjs (přidat téma = jeden řádek) je ta theme-attachment půlka de-risk spike; zbývá jen optimistic.mutate. → Stav Stepperu: ready-to-build — brainstorm + theme-attachment de-risk uzavřeny; optimistic.mutate red-first spike náleží už do build fáze (psaní core kódu), ne do plánování.

Ekosystém — Function-owning appky (zásada 2026-08; pro slevy upravená 2026-09-28, viz konec odstavce): Function appka = dvě extension, jedna appka: storefront (pure surface) zobrazuje efekt, Shopify Function (Rust→WASM) vynucuje/naceňuje u checkoutu; config = jeden zdroj pravdy → storefront přes app-proxy /config, Function přes won.* metafield. Koordinace (blend): každá appka vlastní a nasazuje svoji Function (modularita), ale postavené ze sdílené Rust logiky v packages/functions/* → konzistentní chování, sdílené zaokrouhlování, sdílený won.* metafield schema a jedna „Won stacking policy" (konzistentní combinesWith + zdokumentované pořadí + cross-app awareness jako Toasts↔dárky (dříve GiftLadder, dnes Won Discounts) _gift_progress). Vyhnout se: jeden „hub" vlastnící všechny Functions (zabíjí modularitu) i nekoordinovaným per-app Functions (dvojité slevy). Přesné limity Functions ověřit přes shopify-dev MCP při psaní Won Discounts. Aktualizace 2026-09-28: pro slevy už „žádný hub“ neplatí. Tiers, Rewards, Outlet a MarginGuard se sloučily do Won Discounts, který záměrně vlastní všechny discount Functions obchodu (discount funkce o sobě nevědí, max. 25 aktivních na store → pár uzlů nad jedním configem). Default vzhled = neutrální systémový (auto light/dark přes prefers-color-scheme, jemný stín, sémantické akcenty), design studio je override. Badge: Spec · Scaffold · Alpha · Beta · Shipped.

v2 směr (obecný notification engine): Won Toasts přerůstá z cart-toastů na jednotný notification engine — cart eventy, social proof, announcementy i urgency pod jedním designem, jedním rate-limit/conflict „mozkem" a jednou Shadow-DOM plochou. Odlišení ne počtem funkcí, ale (1) unified engine (konkurence lepí typy po jednom, bez společného frequency budgetu), (2) trust — „real events only", GDPR-first, perf budget, Built for Shopify, (3) jednoduchost / onboarding (presety + progressive disclosure). Cena = radikálně jednoduchá & předvídatelná (flat), s přehodnocením tieru až doroste engine (social proof + analytika + A/B). Zásada (locked): každý page-view typ (social proof, announcement, urgency) je povinně governovaný frequency cappingem (max/session, cooldown, „po zavření už ne", cross-page dedupe) — nesmí ven dřív, než ten gate existuje. Cart eventy zůstávají bezpečné (spouští je jen akce zákazníka). Free-shipping progress bar sem nepatří (řeší Won Discounts, modul Odměny za košík); tady je milestone jednorázový toast, ne page-view spam.

AI-first směr (trust-data bridge, ne AI-shopping-first): nezaměňovat dvě teze. AI-shopping-first (čitelnost pro AI kupce/agenty) je hra tématu, ne appky — social-proof toast je human konverzní taktika, AI agent nezažívá FOMO a popup nevidí; jak roste agentic nákup, adresovatelná plocha klasických toastů se zmenšuje (reálné portfolio riziko, pojmenovat ho). Kde Toasts AI-first dává smysl: (1) jako zdroj trust-dat — už vlastní proprietární behaviorální/prodejní signály (velocity, recency, „N koupilo tento týden"); vystavit je jako strojově čitelný popularity/bestseller signál, který krmí theme won-schema (JSON-LD) → toast přestává být jen popup a stává se trust-data enginem AI-čitelného storefrontu (moat propojující portfolio). (2) AI-powered app vrstva (LLM pro merchanta, ne pro agenta) — už máš ai-advisor-v2 + Insights diagnózu; rozšířit o AI-psanou toast kopii per segment/locale. Zásada: data duálního účelu (human toast i strojový signál), čímž se appka pojistí proti agentic posunu. Napojení: theme-roadmap blok 12 (AI-shopping-first).

Fáze 8 — trust-data bridge (ROZHODNUTO 2026-08-12): vlastní Won Toasts, za Pro planem. Toasts vlastní prodejní data (SaleEvent z orders webhooku), proto zapíše i signál — symetrické se Stepper→won.quantity_rules. Mechanismus: čistý core engine (packages/core/src/toasts/popularity.ts) spočítá per-produkt units sold za N dní + odvozený bestseller (top % nad prahem, ne s 1 prodejem) → app writer přečte nedávné objednávky přes Admin API (read_orders, throttle-safe) a zapíše won.units_sold_30d (number) + won.bestseller (bool) přes metafieldsSet → theme won-schema engine (F1–F8) to přečte SSR: faktický počet do additionalProperty, bestseller jako viditelný badge (žádný fake schema typ). Nový scope: write_products (re-consent). Jen agregované počty, žádné PII.

Obecný vzor „app → won.* metapole → téma (SSR/AI)": tohle NENÍ nový most, je to kanonická konvence portfolia (Stepper Pro čte won.quantity_rules, Won Discounts, Toasts…). Stejným způsobem může theme won-schema engine krmit víc zdrojů: reviews → won.rating → AggregateRating, sklad → dostupnost, Toasts → popularity, Won Discounts → množstevní ceny. AI-renderer (JSON-LD) je vždy téma; appky jsou jen producenti signálu. Pozor na kolizi názvu: theme won-schema engine (schema.org / JSON-LD) ≠ appka Won Schema (metafield-type migrátor) — jiný koncept, stejné slovo.

Poctivé háčky (locked): (a) fake čísla prodávají → „real only" je sázka, co ZUŽUJE trh na merchanty citlivé na férovost, ne celý trh; (b) „real only" vyrábí cold-start problém (nový/malý obchod nemá co ukázat) → naše odpověď: cart eventy jedou od první návštěvy, countdown + announcement jako cold-start výplň, agregovaný social proof až s objemem; (c) unified engine je pro merchanta neviditelný → překládat do benefitu „vypadá to jednotně + nezahltí zákazníka + jedno nastavení"; (d) flat pricing je marketingový wedge proti impression-anxiety, ale přehodnotit až doroste engine. Strategické závěry promítnuté do žebříku níže: onboarding ukrást hned (MVP6), jeden VIDITELNÝ cold-start-safe typ dřív (countdown + low-stock/cart-activity, MVP9) ať MVP6–8 nejsou jen plumbing, vrátit škrtnutý countdown timer a exclude-URLs, a AI hrát se substancí (advisor co reálně konfiguruje/optimalizuje, ne gimmick). Nevyhráváme na šířku — vyhráváme jako čistá, důvěryhodná, dobře designovaná, „nezahltí zákazníka", férově placená alternativa pro segment odpuzený adwarem.

Čtení Function-slev (napojení na Won Discounts): Toasts musí umět oslavit „aktivovala se množstevní sleva", i když ji naceňuje cizí Function (Won Discounts, množstevní slevy) u checkoutu. Napojení je čisté a theme-independent (ověřeno přes shopify-dev): automatická Function-sleva je vidět na storefrontu už před checkoutem — Ajax /cart.js ji nese jako line_level_discount_allocations[].discount_application.title + amount (a cart-level cart_level_discount_applications); v Liquidu totéž přes cart.discount_applications a line discount_allocations. Plumbing (bez druhého fetche): sdílený @won/core/cart už tahá /cart.js (jeden zdroj, won:cart:update) → cartState dostane normalizované discountAllocations (line+cart: {title, amountCents, lineId}) a deriveEvents emituje won:discount:applied|changed|removed při změně množiny alokací. Atribuce (load-bearing kontrakt): Toasts smí oslavit jen slevu, kterou umí přiřadit k Won appce — proto Won Functions stampují title/message v rezervovaném won.* namespace (např. marker won-discounts:, dříve navržený won-tiers:; lidská část zůstává čitelná „Množstevní sleva 3+ ks"); parser žije ve sdíleném packages/functions (unpark až s Won Discounts). Poctivost (doktrína „no toast > wrong toast"): neznámý title (kupón, merchantova ruční sleva) → mlčet, nikdy ho nevydávat za množstevní slevu. Arbitráž: Toasts je renderer/arbiter (jeho grouping / rate-limit / conflict engine z MVP3), Won Discounts je jen zdroj typed signálů → jedna alokace = jeden toast, žádné dvojité oslavování. Timing: alokace je v /cart.js až po server-reconcile, takže toast se pouští na reconciled cartState, ne na Stepperově optimistickém — jinak bys oslavil slevu, kterou server nepotvrdil. Primitiv drží: Toasts vlastní notifikaci, Won Discounts vlastní cenu — Toasts jen přečte hotovou alokaci (odkaz, ne vlastnictví; viz „Hranice portfolia").

0 · Nápad (M·migrator): typ existující definice metapole nejde změnit — MetafieldDefinitionUpdateInput nemá pole type (ověřeno proti schématu 2026-04). V migratoru: examples/reference-migrations/hotfixes/legacy-utils/migrate-metafield-type.mjs (journal na disku, resumovatelný restore) + scripts/audit.mjs, scripts/rename-metafield-values.mjs, scripts/backfill-metafield-values.mjs.   1. Klon: rsync z apps/_template/ (standardní vyloučení dle README), přejmenovat, npm install, npm run config:link -w won-schema.
  2. Core modul: packages/core/src/schema/convert.ts — convertValue(raw, fromType, toType) jako čistá funkce pro dvojice typů (text ↔ rich_text ↔ list.*, number, boolean) s explicitním UnsupportedConversion místo tichého průchodu; + planMigration({definition, values, targetType}) vrátí seznam nekonvertovatelných hodnot před zápisem. + node:test na každou dvojici typů a na odmítnutí neznámé konverze.

Záloha hodnot i metadat definice (description, pin, access, capabilities) musí být commitnutá v DB dřív, než se zavolá metafieldDefinitionDelete — jinak přijde merchant o data.   8. Gate: test:unit, typecheck, build (-w won-schema) + npm run validate:shopify.
